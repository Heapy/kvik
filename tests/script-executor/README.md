# JVM script executor boundary

`JvmScriptExecutor(runId, runDirectory, workingDirectory, host, content, toolchains)` consumes the typed `jvmScriptAction` contract. It reconstructs that contract into independent collections, verifies the requested tool identities through `JvmToolchainProvider`, and materializes all declared CAS inputs in a fresh private directory. `workingDirectory` is the caller's project or standalone companion root; script effects there are intentional. This is process ownership, not an application sandbox.

Main discovery examines only the script's own materialized `.class` files, with SHA-256/size checks and the existing 20,000-class, 256 MiB aggregate, 64 MiB per-class bounds. Dependency mains are excluded. Declared classpath order is preserved, followed by the provider's verified Kotlin standard library. The order permits explicitly declared classes/libraries to take precedence; the suite proves argv order, not compatibility of arbitrary replacement stdlib versions. `--disable-@files` preserves literal script arguments. The fixed base environment plus declaration is passed explicitly; ambient JVM flags are not inherited. Java receives private temporary/home system properties and explicit UTF-8 stdout/stderr encoding, while its process cwd remains the supplied root.

`observations` returns `JvmScriptObservation` values with the action result, `SETUP`/`MAIN_DISCOVERY`/`EXECUTION` phase, nullable exact host `ProcessResult`, cancellation latch, selected main, private directory, exact argv, tool-bound stdlib path, and diagnostics. Setup and discovery failures have no child exit. Main-selection failures are configuration diagnostics. EXECUTION means an owned launch was attempted; it does not certify Java entered main. The additive host `setupFailure` retains a bounded setup stage and errno. A guardian setup failure uses `KVIK_SCRIPT_LAUNCH_FAILED`; a user choosing the same exit value has a null setup failure and uses `KVIK_SCRIPT_EXIT`. Cancellation and timeout retain priority while preserving any observed setup detail.

A terminal process observation is published only after `poll` and `close` prove complete cleanup. Protocol/cleanup exceptions propagate rather than becoming ordinary child exits. Early close drains ownership without inventing a result that the host did not return. Requested cancellation remains cancellation even if the host already observed exit zero, and the original host result is retained. Actions have no cached outputs and always use NEVER. Each invocation retains separate `script.stdout` and `script.stderr` files.

The executor and stores are thread confined. Callers must keep verified tool installations, cwd, CAS and private run roots stable during use. Materialization uses the supplied store's supported blob bound; it does not add an independent 64 MiB artifact limit. Main-discovery buffers alone have the bounds above. ByteArray materialization still allocates one artifact at a time, and main discovery retains its bounded aggregate map. The production provider's full inventory verification remains a separate integration boundary.

It records source/support/tool identities, complete commands/environments/logs, class outputs, binary hashes, exact requests/observations, stream/effect files and immediate post-terminal child checks. There are now 14 fake-host/real-CAS groups and six real-Java groups (ten invocations); the additional group checks host setup failure retention. The fixture provider freshly hashes the consumed Java launcher and stdlib for every call; it does not claim to replace complete installed-JDK or worker-bundle verification. Those are tested by the production provider gate. SDK, JDK support and Native dependency trees must remain stable during compilation; the receipt does not claim their complete inventory.
