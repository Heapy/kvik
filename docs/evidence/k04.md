## Integration

`NativeContentStore(root, maxBlobBytes, diagnostic)` implements `ContentStore`. `NativeActionCache(root, content, diagnostic, maxRecordBytes)` implements `ActionCache`. `NativeOutputTrees(content)` exposes `capture(root): TreeManifest` and `materialize(manifest, destination)`. Roots and destinations are normalized absolute paths. Parent directories of a materialization destination must already exist. The destination itself must be absent, including when another process creates it during restoration.

```kotlin
val content = NativeContentStore("/absolute/run-cache/cas", diagnostic = ::recordCacheDiagnostic)
val actions = NativeActionCache("/absolute/run-cache/actions", content, ::recordCacheDiagnostic)
val outputs = NativeOutputTrees(content)
val manifest = outputs.capture("/absolute/completed-action/output")
actions.publish(CachedAction(actionKey, manifest))
// After lookup returns a hit:
outputs.materialize(manifest, "/absolute/run/unique-restored-output")
```

The executor must call `publish` only for successful cache-eligible actions. The v1 `CachedAction` interface does not carry status or action kind, so this adapter cannot infer execution eligibility. Tests/scripts/publication effects still execute on every request. The executor owns diagnostics translation from `CacheDiagnostic(code, message)` into core diagnostics/events. A missing or unreadable blob produces `blob-unavailable`; verified size/hash mismatch produces `blob-corrupt`; oversized reads produce `blob-too-large`. Action misses produce `action-unavailable` or `action-blob-missing`. Successful invalid-entry eviction reports `blob-repaired` / `action-repaired`. Writes and restore failures throw `CacheFailure` or argument validation exceptions; callers must report them appropriately.

Local disk records are canonical v1 JSON with `schemaVersion`, `key` and `outputs`. Blobs use `<sha256>-<size>` names under `blobs/`; action records use `<sha256>-<size>.json`. This is a local format, not REAPI transport.

## Publication and restore guarantees

Blobs are written to unique staging files, normalized to mode 0444, fsynced, and linked into the final name without replacement; the containing directory is then fsynced. Same-key writers use persistent `flock` inodes. Correct existing blobs retain their inode. Confirmed invalid bytes/types can be unlinked under that lock before the replacement is published; a reader during this interval can observe a diagnosed miss, never a partially written replacement. Unreadable regular-file I/O errors preserve the entry and fail the write. Directories at blob/record addresses are refused, not recursively removed. Kernel lock ownership ends when a process dies; lock files must not be deleted while producers run.

Action publication first reads/verifies every referenced blob and durably re-publishes it through the content store. It then uses the same staged-file publication and directory fsync for its record. Invalid records can be repaired under a persistent per-action lock; a valid record with different outputs is a conflict and cannot be overwritten. Readers validate record structure, key, and all referenced blobs before returning a hit. No cache eviction or garbage collector runs concurrently with this process.

Restoration creates a private staging directory beside the destination. Logical paths are validated by the core manifest. Every implicit directory uses exclusive creation, and every file uses `O_EXCL | O_NOFOLLOW`; distinct spellings that alias on the actual filesystem therefore fail. Blob contents are verified again before writing. Files normalize to 0444 or 0555; directories use 0700. After files and directories are fsynced, Darwin `renamex_np(RENAME_EXCL)` atomically exposes the complete directory while refusing every existing destination. Failed pre-exposure restores clean their staging tree. Capture inventories regular files recursively and rejects symlinks and special files. Empty directories have no identity and are not restored.

## Boundaries and remaining gaps

- This adapter targets local macOS arm64 filesystems. Linux/Windows, network filesystems and their lock/durability semantics have not been implemented or verified. Native POSIX calls plus Darwin exclusive rename stay confined to `NativeFiles.kt` except exclusive directory creation in `OutputTrees.kt`.
- Roots are caller-owned. Capture requires a quiescent producer tree, and cache/output ancestors must not be renamed or replaced by hostile concurrent processes. Existing symlinks are rejected; full descriptor-relative protection against an adversary racing ancestor replacement is not claimed. Do not share writable cache roots with untrusted users.
- The public contract is whole-buffer `ByteArray`. Default limits are 64 MiB per blob and 16 MiB per action record, configurable at construction. Reads and publication allocate complete byte arrays; snapshot copies, existing-content comparison and core SHA-256 padding add multiple artifact-sized allocations. Memory grows with concurrent calls. This is suitable for initial small artifacts, not large archives; streaming hashing/transfer and a global byte budget remain future work.
- SIGKILL can leave `.kvik-stage-*` directories. They are never lookup candidates and do not block later producers; stale staging cleanup, quotas, eviction and garbage collection are not implemented. Cleanup must coordinate with active writers and preserve live lock inodes.
- `fsync` ordering is implemented and process-kill scenarios are tested. Sudden power loss, disk-full/permission fault injection, and Darwin drive-cache `F_FULLFSYNC` guarantees are not claimed.
- No remote K07 transport, cache authentication, remote execution, or launcher lifecycle integration is included.
