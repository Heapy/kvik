# K14 local source bootstrap (partial)

The root `kvik` launcher compiles core, cache, execution, CLI and the local `plugins/kotlin` build plugin into a **Kotlin/Native** macosArm64 executable. It also compiles and bundles K03's small C ownership guardian and statically links the native process bridge. The runtime supports `help`, `runtime-info` and read-only `inspect`. The plugin registers its schema; consumer action construction is not connected yet and fails explicitly if requested. This is a source-composition implementation, not a completed consumer build tool.

## Identity and publication

`bootstrap/composition.json` selects sources and the plugin registry. `runtime.lock.json` binds content inventories, plugin API version, registry implementations, compiler arguments, bootstrap recipe, platform, declared environment and complete installed-tool inventory digests. Source identities use file contents and executable bits, not modification times. Consumer files outside the runtime composition do not alter its identity.

`bootstrap/toolchains.lock.json` records explicitly provisioned Kotlin/Native 2.4.20, Liberica JDK 25.0.4, native LLVM/libffi dependencies, the macOS SDK and Xcode toolchain. This lock is for the observed Apple M4 Max host with macOS 27.0.1 (Darwin 27.0.0), Xcode 27.1 and SDK 27.0. The repin command is an explicit maintenance operation; ordinary startup never silently repins. Native compilation uses the verified SDK/developer directory and offline Kotlin/Native dependencies.

Per-composition file locks serialize producers. Builds use private snapshots and staging directories. Successful publication includes the executable digest, effective runtime lock and manifest; a directory rename exposes the completed entry. Cached startup checks the executable bytes, executable permission and lock identity. Corrupt entries are quarantined before replacement. A failed rebuild does not run an older composition. Interrupted staging directories cannot qualify as published cache entries.

## Foreground compiler ownership

Before the native runtime exists, a small Python source guardian owns each bootstrap compiler process group. An inherited read pipe signals loss of the invoking launcher, including launcher SIGKILL. Compiler children cannot inherit the ownership pipe. The guardian observes completion with `waitid(WNOWAIT)`, sends TERM followed by KILL to the group, and reaps the leader only after cleanup; the unreaped leader reserves its process-group identity. No socket, daemon or reusable background service is created. Normal launcher exit waits for the guardian.

`tests/bootstrap/test_ownership.py` passed five real-process tests: declared environment/cwd/output and failing exit; rapid completion and failed exec; timeout; normal leader exit with a remaining descendant; and INT/TERM/KILL of one owner while another invocation remains running. These use TERM-resistant fixture processes and an external `ps` observer. The observer requires process-inspection permission in the development sandbox. Initial testing found and corrected swallowed signal exceptions inside Python subprocess waits and Darwin's EPERM result for an exited group containing only zombies.

The supported boundary is an ordinary same-user compiler process group. Deliberate daemonization, changed credentials, direct guardian SIGKILL/STOP and uninterruptible kernel operations are not handled. The Python bootstrap guardian also owns the clang, archive and cinterop steps that construct K03's native helper/bridge. Every platform source is snapshotted and pinned. The published bundle contains both executables; the helper's bytes are verified at cached startup and its expected digest is compiled into the Kotlin/Native runtime. The native runtime locates the helper relative to its actual executable, never from PATH or an environment override, and verifies it before constructing a process host. Consumer CLI process orchestration remains K09 work.

## Reproduction

```sh
python3 tests/bootstrap/test_identity.py -v
python3 tests/bootstrap/test_ownership.py -v
python3 tests/bootstrap/test_launcher.py --java-home "$JDK" --konan-home "$KONAN"
./kvik --java-home "$JDK" --konan-home "$KONAN" -- runtime-info
python3 tests/bootstrap/test_launcher.py --java-home "$JDK" --konan-home "$KONAN" --quick
```

Six identity/cache-metadata tests pass, including the shared canonical identity vectors, content changes with preserved size/time, executable bits, symlink rejection, malformed JSON, malformed cached manifest shapes and rejection of unmodeled compiler flags. External KLIB/compiler-plugin file options are rejected until dependency content can enter the runtime lock.

The black-box suite passed 14 checks on 2026-10-22: interrupted real bootstrap without publication; concurrent producers; relocated checkout; independent core, native options, registry and tool-lock edits; consumer-only edits with absent compilers; same-size/same-mtime plugin edits; plugin recomposition; corrupt binary rejection/rebuild; failed compilation without stale fallback; and reuse after restoring sources. The original copied-checkout composition was `601da8b9417ad261dc256ae13388f5fa5b8bf92a5ca241c3d9cc7a928b746b9d`.

With all tools provisioned, the concurrent empty-executable-cache run took 40.624 seconds and performed one compile; plugin recomposition took 37.158 seconds. These include full installed-tool verification. They exclude tool download/provisioning and are individual observations, not stable performance claims. The suite retains raw measurements in `.kvik/tests/bootstrap/integration.json`; a durable copy is in `k14-bootstrap-summary.json`. Retained measurements must identify the exact composition: changing bootstrap or core source intentionally changes that identity.

Independent review found and corrected malformed-cache handling, the publication-directory fsync, an oversized guardian error-message pipe deadlock and untracked file-bearing compiler options. Targeted regressions and the full launcher suite passed after these fixes.

The subsequent native-helper composition passed the expanded **16-check launcher suite**, adding helper-source invalidation and corrupt-helper rejection. Its composition is `84242ff0c6e9bb6e00df48ea728e2140b2b7ceccc5633ad20217845da7f512d7`. Six Native CLI/inspection checks also pass, including relocation of the actual executable/helper bundle and toolchain diagnostics when a corrupted helper is encountered through direct native invocation. Ten cached offline launches took 0.4499 seconds total (42.9–54.3 ms each). These observations ran alongside other compiler/review work and are not isolated benchmarks. The expanded raw results are retained in the summary's `bundledNativeHelper` section. Independent review found no confirmed defect in this helper integration.

## Remaining K14 work

- Acquisition and immutable locking of remote source distributions; current inputs are local source trees.
- Build-plugin dependencies/native libraries beyond the local example and their compatibility rules.
- Shared K04/remote executable cache integration and lifecycle verification of the complete consumer-build CLI.
- Tool provisioning on another host, cross-machine portability, cold provisioning measurements and additional host targets.
- Orphan staging/quarantine reclamation and broader filesystem failure testing. The cache assumes caller-controlled stable ancestor directories; it is not a hostile-filesystem sandbox.

Fast cached help is not evidence of working consumer compilation, test avoidance, continuous mode or remote reuse. Those gates remain open.
