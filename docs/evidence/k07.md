## API and eligibility

`RemoteActionCache` wraps existing `ContentStore` and `ActionCache` instances. Its action-aware API is necessary because a bare local digest cannot construct a REAPI Action:

- `lookup(action): Hit?` returns a verified local hit first, otherwise an eligible verified remote hit, otherwise a diagnosed miss. `Hit.remote` distinguishes the origin.
- `publish(action, result): Boolean` accepts only a matching `EXECUTED` result with exit code zero and declared output paths. It publishes valid local metadata first and returns whether remote publication also succeeded.
- `remoteEligible(action)` requires `REMOTE`, a cacheable kind, and an exact configured `PortabilityApproval` matching implementation/version, target and full platform attributes. There are no default approvals. The approval includes an evidence reference for the caller to audit.

Test, script, publication, benchmark and server effects never use this adapter's cache paths. There are no execution-service RPCs and no inferred remote execution capability. The fixture's byte-producing synthetic adapter is the only approved combination in tests. **No Kotlin compiler adapter or cross-machine compilation portability has been established.** K06/K10 must supply real portability evidence before an integration adds such an approval.

The production integration must validate compiler/tool paths and declared arguments according to the existing adapter contract. For this mapping, `ActionSpec.arguments` must contain the complete declared command vector, including an executable name; the client does not invent a compiler command from options alone. Inputs and arguments use the same logical root, and declared output roots must not overlap.

`RemoteEndpoint` requires explicit trust in cache writers. TLS uses system certificate/hostname verification; HTTPS endpoints are supported, and unencrypted HTTP is restricted to explicit `127.0.0.1:port` fixtures. Bearer credentials are optional transport configuration and never enter action identities. Proxy environment settings and redirects are disabled; diagnostics report generic transport/HTTP/gRPC failures without header contents or credentials. TLS/authentication have not been exercised against a deployed authenticated service in this milestone.

## Protocol mapping and integrity

The handwritten bounded protobuf subset follows the upstream [REAPI v2 schema](https://github.com/bazelbuild/remote-apis/blob/main/build/bazel/remote/execution/v2/remote_execution.proto). The schema bytes inspected for this implementation have SHA-256 `4c5b4cd802dc1e2a9e1500c01821924c6135b2a11388e79905c540d010c9082b`. The actual interoperability peer is the pinned backend above; this is not a generated implementation of every REAPI message.

The remote action identity hashes a serialized REAPI `Action` containing command digest, input-root digest, timeout and platform properties. Its salt is `kvik-reapi-v1:<local SHA-256>:<local size>`, binding every remaining resolved Kvik action field, including composition, implementation, target, toolchain identities, parameters and cache policy. This versioned salt supplements the normal REAPI graph; the client does not use an opaque local hash as the remote action digest.

`Command` carries ordered arguments, name-sorted declared environment and sorted output paths. The input root is a real recursive Directory Merkle tree: sorted FileNode/DirectoryNode names, content digests and executable flags. Protobuf scalar defaults are omitted; repeated empty arguments are preserved. Names are sorted by UTF-8 bytes. Every Directory, Command, Action and input/output content blob is uploaded before the action result is committed. Digest size and SHA-256 are checked before upload, on every CAS download and before local publication.

Exact declared file roots map to `OutputFile`; declared directory roots map to `OutputDirectory` with a CAS `Tree` containing the root and deduplicated child directories. Incoming results must have exit code zero. Logical paths and declared roots are validated; symlinks, unsupported node properties, duplicate/colliding names, missing child directories and excessive expansion are rejected. K04 materialization subsequently rejects aliases on the actual destination filesystem and exposes the restored tree atomically. Remote lookup only imports verified content and metadata; it does not expose output files itself.

The client negotiates SHA-256 support, action-write permission and batch limits through `GetCapabilities`. It uses unary `BatchUpdateBlobs`, `BatchReadBlobs`, `GetActionResult` and `UpdateActionResult`. Each batch contains one blob, every per-blob status/digest is checked, and action metadata is sent only after all CAS acknowledgments. Interrupted uploads may leave harmless content blobs. The server's returned ActionResult is decoded and compared with the expected output manifest. Backend eviction/races remain possible; every later lookup re-verifies availability. A failure during or after `UpdateActionResult` can leave a valid remote entry; a false publication return means no confirmed complete acknowledgment, not proof that the entry is absent. The client does not claim remote power-loss durability beyond the server's acknowledgments.

The libcurl bridge requires HTTP/2 and HTTP 200, a valid application/grpc content type, a single uncompressed message and a successful gRPC trailer. It bounds response memory and headers, refuses redirects, and closes its native handles after each RPC. No curl worker or other runtime child process exists.

## Bounds and unsupported cases

Default limits are 1 MiB per blob (including mapping/Tree messages), 2 MiB per RPC body/frame, 32 MiB cumulative framed request/response payload per operation, 2,048 RPCs, 4,096 files, depth 32, 3 seconds per RPC and a 30-second network-operation deadline. Headers are separately capped at 64 KiB per RPC. Publication preflights aggregate content and mapping payload against half the cumulative payload budget. Limits are configurable within hard maxima; exceeding a limit yields a diagnosed remote miss/failure. Tests tighten per-RPC/operation deadlines to 500 ms/5 seconds.

This is a whole-buffer client: local blob reads, protobuf construction/parsing and libcurl/Kotlin copies allocate several payload-sized buffers. Transfer budgets do not constitute a process RSS budget. Parsing/identity work is bounded by message/file/depth limits but is not preempted by the network deadline. The API is synchronous and must run in a bounded cache-I/O phase or dedicated worker, not directly on a responsive scheduler/control thread. It has no independent asynchronous cancellation API; active requests terminate at their configured deadline. Caller state and the local adapters are single-caller confined.

Large-blob ByteStream streaming, compression, retries/backoff, remote execution, gRPC multiplexing, non-SHA-256 digests, output symlinks/node properties, mTLS/custom CA configuration, shared-cache authentication enforcement and distributed writer conflict resolution are not implemented. Inline output bytes are integrity-checked, but this subset still requires their CAS content to be available. Stdout/stderr are not part of the core cached-output contract; referenced log blobs are verified but not materialized as outputs. Empty directories have no Kvik artifact identity.

This milestone does not establish K10 cross-machine portability, production backend deployment policy, compiler integration or CLI/runtime composition integration. The latter must include the new C bridge, Kotlin sources and libcurl/host compatibility identity in the composed runtime.
