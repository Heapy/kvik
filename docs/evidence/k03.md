# K03: native local execution

Date: 2026-10-22. Host: macOS ARM64. This evidence covers local execution; compiler adapters, cache publication, foreground control and source-built launcher integration are separate milestones.

## Implementation

`execution/src/kvik/execution/Scheduler.kt` implements `SchedulerRun` over the K02 `ActionNode` and `ActionExecutor` contracts. It validates the entire graph before starting work, resolves only successful declared predecessors, snapshots resolved collections, and uses sorted action IDs for scheduling and polling ties. It shares eligible identical action keys only within that run; actions with `CachePolicy.NEVER`, including requested effects, always execute individually. Deduplication preserves the original execution status rather than inventing a cache hit.

Each run has a parallelism and memory budget. Resource requests larger than the budget fail explicitly; exclusive names serialize actions within the run. Failed prerequisites block dependents while independent actions continue. Cancellation reaches every active handle and prevents queued work from starting. Journal or adapter failures close owned work. The scheduler emits action events only, with local sequence numbers increasing from one; `NativeEventJournal` appends and fsyncs each event before returning. The CLI/run coordinator owns authoritative `run-started` and `run-finished` events because it knows requested checks, input snapshots and the complete verification record. When combining event sources, that coordinator must assign run-wide sequence numbers before persistence. Event ordering is stable for a given sequence of observed completions, not a promise of identical wall-clock completion ordering between parallel executions.

`ProcessActionExecutor` bridges actions to a `ProcessHost`. A compiler adapter supplies the isolated process paths and a validated output collector, which runs only after successful exit. The executor rejects a different owning run ID. It does not publish caches or infer outputs from arbitrary directories.

`NativeProcessHost` uses the small C boundary in `execution/platform/process.c`. It launches a separately source-built `guardian.c` executable for each worker with explicit environment, cwd, separate new stdout/stderr files and a timeout. Executables and paths must be absolute; there is no executable PATH lookup. Worker stdin is `/dev/null`. Log files use `O_EXCL | O_NOFOLLOW`. Invocation directories are reserved atomically with `mkdtemp`.

The guardian is an invocation-owned process, with no service socket, persistence, reuse, or daemon mode. It forks before running any Kotlin code, places the worker in its own process group before exec, and watches an owner pipe. Cancellation closes that pipe; owner death also closes it in the kernel. Every completion path sends TERM to the worker group, allows 200 ms, sends KILL, then reaps the direct worker. Normal worker exit also cleans any remaining group members. The group leader is observed with `waitid(WNOWAIT)` and remains unreaped until cleanup, reserving its PID/PGID against reuse. The host reaps the guardian. Pipes are close-on-exec and the macOS spawn bridge explicitly inherits only the guardian protocol descriptors, so one worker cannot keep another run's ownership pipe alive.

## Reproduction

From the repository root:

```sh
python3 tools/test_execution.py \
  --konan-home /Users/yoda/.konan/kotlin-native-prebuilt-macos-aarch64-2.4.20 \
  --java-home /Users/yoda/.sdkman/candidates/java/25.0.4-librca
```

The script compiles the guardian with host Clang and `-Wall -Wextra -Werror`, builds the C interop library with the pinned Kotlin/Native distribution, and compiles/runs native scheduler tests and a native process probe. The JDK is used to run the compiler, not the Kvik orchestrator. Builds go into `.kvik/tests/execution/`. The external Python observer needs permission to run `ps` on its own test processes; the restricted agent sandbox denied that observation, so the final successful run used approved process-observation permissions.

Install the pinned development-only dependencies from `tools/schema-requirements.txt` for JSON Schema assertions. The event-contract correction was verified with the same command plus `--scheduler-only`: eight native scheduler tests and the real-process DAG passed, and every persisted action event validated against the K02 schema. The checks include prerequisite completion before dependent start, start before finish, and cleanup/prevented dependent launch when completion-event persistence fails. Process guardian code did not change; the external lifecycle matrix was not rerun solely for that event correction.

Observed final result: **7 native scheduler tests passed; all native process checks passed.** Checks cover dependency resolution, sorted scheduling, deduplication, repeated requested effects, independent runs, memory/exclusive/parallel limits, dependent blocking with independent failures, cancellation, invalid graphs, oversized requests, and cleanup on journal failure. A six-node DAG also runs through the real native process adapter, verifies one eligible duplicate executes once, two identical tests execute twice, and all six action results are persisted.

External process checks observed:

- Declared environment present; an undeclared parent variable absent; cwd correct; stdout/stderr separated; child exit 7 preserved.
- Cancellation, host close and timeout stop a shell and descendant that both ignore TERM, within the three-second test bound.
- Killing the native owner with SIGTERM, SIGINT and SIGKILL stops its worker, descendant and guardian while another invocation's worker and descendant remain running.
- Ordinary leader exit stops a remaining TERM-resistant descendant while preserving the leader's successful exit status.
- Events remain readable after owner exit, with contiguous sequence numbers.

An earlier run timed out waiting five seconds for a hold-mode descendant PID file. The complete rerun passed, and an additional 30 native owner/guardian startup and abrupt-owner-exit cycles passed. No cause was established for that earlier startup observation; it should not be represented as a repaired lifecycle defect. The repeated-cycle check established startup and owner exit, not a separate process-tree inspection for each of its 30 cycles.

## Guardian integration protocol

Build `execution/platform/guardian.c` into the same verified runtime composition as the native executable. Hash the source, compiler/build recipe and resulting helper binary; do not select a helper from PATH. Source-built launcher integration owns those identity checks.

```sh
clang -std=c11 -D_DARWIN_C_SOURCE -Wall -Wextra -Werror \
  execution/platform/guardian.c -o guardian
```

Argument vector: `guardian cwd stdout_file stderr_file timeout_ms executable arg...`. The helper's environment is exactly the worker environment. Descriptor 3 is the read end of the owner pipe; descriptor 4 is the write end of the result pipe. All other ownership pipes must be close-on-exec/non-inherited. On cleanup completion, the result pipe receives three native C integers: exit code, timeout flag, cancellation flag. This is an internal same-host protocol, not a cross-platform wire format. Codes 124, 130, 125 and 127 respectively identify timeout, cancellation, setup/infrastructure failure and exec failure; ordinary child status is preserved. The parent must wait for guardian exit and reap it, not treat receipt of the result alone as completed ownership cleanup.

## Limits

- Supported platform is macOS ARM64. No Linux/Windows lifecycle claim is made.
- The ownership boundary is a process group, not an OS sandbox. Descendants that deliberately call `setsid` or move to a different process group escape it. Such daemonizing adapters are unsupported.
- SIGKILL or SIGSTOP delivered directly to the guardian, or simultaneously to the owner and guardian, cannot be handled by the guardian. Owner-only SIGKILL is tested and supported.
- Group members are stopped, but orphan grandchildren are reaped by macOS init; only direct children can be reaped by this implementation. Observer checks treat a zombie as stopped, not as still executing.
- An OS-uninterruptible child can delay reaping despite KILL. The 200 ms grace and observed test bounds do not promise recovery from a stalled kernel or unavailable filesystem.
- `SchedulerRun` and `NativeProcessHost` are confined to one caller thread. Resource/exclusive budgets are per run; global resource arbitration is not implemented.
- Session input EOF/reload/control handling belongs to K15. Callers must call `cancel`/`close` for those controls. Owner termination is independently covered by the guardian.
- The source-built launcher must verify/build the helper with the runtime composition; this execution slice alone does not establish launcher provenance or K14 completion.
