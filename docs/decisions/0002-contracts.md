# K02: prototype contracts, version 1

Date: 2026-10-22. Status: initial contracts, with executable vectors. Changes require an explicit schema/API revision or a coordinated migration before integration.

## Layout and format

`core/src/kvik/core` contains framework-free Kotlin types, JSON parsing, canonical identity and graph validation. These compile with Kotlin/Native; no JVM classes or compiler implementation classes appear in the core. Platform effects belong in adapters.

`schemas/v1/contracts.json` contains JSON Schema 2020-12 definitions for project configuration, artifacts, actions, runtime and dependency locks, compiler workers, inspection, diagnostics, events and verification. Reference a definition with `#/$defs/<name>`. The `https://kvik.dev/...` identifier is a logical schema identifier, not a hosted service dependency. Examples are in `schemas/examples`. Schema validation is supplemented by semantic checks in Kotlin; schemas alone cannot validate graph cycles or evidence completeness.

The initial consumer configuration is `kvik.json`. JSON avoids adding a broad YAML/TOML parser to the native bootstrap. This changes PLAN.md's initially proposed authoring syntax, while retaining declarative configuration and the same project model. Comments and executable expressions are not supported. Unknown schema fields and schema versions are errors, rather than silently ignored options. All source/resource directories are relative to the project root; recursive inventories include relevant untracked files and reject symlinks. Module/source-set names are unique within their containing scope. Source-set dependency edges are explicit; shared sources are included through transitive `dependsOn` edges. Target compilations select main/test source sets. Validate cycles and target/source-set references before execution.

The v1 configuration admits `jvm` and `macosArm64`. A schema-valid target is not a promise that an adapter is available. Inspection reports implemented capabilities; an unavailable requested check produces incomplete verification. Compiler-plugin and script fields reserve their K12/K13 contracts; CLI execution must reject them until those adapters are implemented.

## Canonical bytes and identities

Identity encoding is `kvik-json-v1`: UTF-8 without BOM or trailing newline, object keys sorted by UTF-16 code units, array order preserved, no whitespace. Strings preserve Unicode without normalization, escape quote and backslash, and encode every U+0000–001F character as a lowercase four-digit `\u` escape. Reject unpaired surrogates and duplicate keys. Numbers are signed 64-bit decimal integers; floating-point values are unsupported. Input `-0` canonicalizes to `0`. This is a restricted format, not a claim of RFC 8785 compatibility. Decode input UTF-8 strictly at platform boundaries before parsing.

Every digest is SHA-256 plus byte length. A tree is a sorted flat inventory of files containing logical path, digest and executable bit. Directories are implicit; empty directories have no artifact identity. Paths are relative POSIX paths with no empty, dot or parent segments, backslashes, colons or control characters. Reject symlinks, devices and file/directory collisions. Preserve case and Unicode exactly; materialization must reject names that alias on the actual target filesystem. Permissions normalize to executable/non-executable, not uid/gid or arbitrary mode bits. Content changes invalidate regardless of timestamps or file size. Sorting a set-like inventory is permitted; never sort ordered classpaths or compiler options.

An action key hashes the complete resolved `ActionSpec`: schema and implementation version, native runtime composition digest, kind, execution platform, target, toolchain identities, input tree, output roots, ordered arguments, declared environment, adapter parameters, timeout and cache policy. Build-node IDs are display/graph identities, not part of the action key. Prerequisite output content must be added to the input tree before computing a key. Inputs are immutable after resolution; copy mutable collections at boundaries and never edit an in-flight action.

Action arguments and parameters use logical paths. The adapter maps them into separate `input/` and `output/` directories in a unique run/action working directory. Absolute checkout locations must not leak into portable keys. Tool locations are resolved from verified toolchain identities. Tool flags must not escape the declared input/output boundary or silently override controlled compiler settings. Undeclared host dependencies force local-only or non-cacheable execution. A plugin declaring `REMOTE` is not enough: the executor also requires that adapter/version/platform combination to have passed the portability gate.

The runtime composition identity hashes the canonical runtime lock. Source pins contain immutable Git commits or archive digests plus the complete extracted source-tree digest; local sources use their current tree digest. Acquisition never executes plugins. Source roots map to stable logical IDs. The lock also includes static registry order, plugin API version, toolchain/library digests, bootstrap recipe, ordered options, environment and host/SDK compatibility identity. Consumer source and ordinary consumer configuration do not enter this lock. The launcher must verify tools and source inventories, publish binary plus manifest atomically under a per-key lock, and reject mismatched/corrupt binaries. Those behaviors belong to K14, not the example lock (whose empty digests are illustrative).

## Resolution and compiler contracts

Separate `resolve` from build execution. Exact Maven coordinates and named HTTPS repositories are v1 inputs. Reject snapshots, ranges, dynamic versions and unsupported metadata semantics explicitly. `VariantRequest` distinguishes Kotlin platform, usage and full requested attributes. A lock records selected artifacts, repository/variant provenance, and every metadata digest used in selection. Preserve dependency/classpath order deterministically. Locks bind to effective configuration identity; locked builds never silently update selections. Offline reuse requires all locked blobs to be present and verified. K05 will establish the actual fixture-supported metadata subset before integration.

The native runtime owns worker lifetime. The first JVM worker consumes one UTF-8 JSON request file and writes one JSON result file, using `workerRequest`/`workerResult`; stdout/stderr are logs. Requests use paths inside the controlled action directory and explicit classpaths, plugin classpaths, compiler identity and ordered options. The orchestrator verifies these paths and identities before launch. Result/request IDs must match. Atomic result publication and worker exit are both required: missing/truncated results, compiler crashes, nonzero exit or mismatched success are infrastructure failures. Compiler errors carry structured diagnostics. The worker uses BTA in-process execution; no daemon fallback. Compiler workers cannot outlive the foreground owner. Warm session reuse, when added, must preserve this isolation contract.

Kotlin compiler plugins are compiler inputs, separate from native `BuildPlugin` implementations. Workspace plugin edges participate in ordinary cycle detection; build their artifacts before resolving consumer actions. Plugin implementation content, full plugin classpath, options and declared files enter the consumer key. Build-plugin implementation is conservatively covered by the native composition digest. `@Task` effect analysis remains research and supplies no purity guarantee in v1.

## Execution and caching

`ActionNode` lists prerequisites and resolves an immutable action from their successful results. Validate missing edges and cycles before launching anything. Deduplicate identical eligible action keys within one run; never deduplicate or cache requested test/script/publication/benchmark/server effects. Failure blocks dependents and preserves independent failures in the result. The executor polls running actions so scheduling, controls and cancellation stay responsive. Resource budgets bound concurrent work and memory; exclusive resource names serialize actions that share external state. Tests are parallel by default at independent module/target granularity, with serial/exclusive controls.

Each invocation gets a unique run directory and process ownership domain. Each process receives an explicit environment, working directory and separate stdout/stderr files. Registration and signal handling must avoid an unowned child window. On cancellation, timeout, quit, end-of-input, normal completion or owner loss: stop owned process groups, wait a bounded grace interval, force termination, and reap. A foreground watcher/supervisor may own descendants only while the invocation/session exists. Do not kill by executable name or share cancellation between runs. K03 supplies scheduling/process implementation; K15 supplies the continuous state machine and terminal/control lifecycle.

`ContentStore` verifies both size and hash on reads, atomically publishes immutable blobs and treats corrupt/missing data as a miss with diagnostics. `ActionCache` publishes metadata only after every referenced blob is durable. Restore into an isolated temporary directory, verify the complete output manifest, then atomically expose it. Reject path escapes, symlinks and filesystem alias collisions. Failed, cancelled or partial executions never publish successful metadata. Tests run every time, including after compilation cache hits. Output manifests are public artifacts; mutable compiler incremental state stays outside shared caches.

Remote transport is REAPI v2 against the pinned existing backend. K07 maps canonical action contracts to valid REAPI Action/Command/Directory blobs and ActionResult outputs; merely storing arbitrary opaque action keys is not the protocol contract. Trusted writers only, credentials outside action identity, bounded transfers, verified blobs and safe local fallback. Remote execution is not part of this milestone.

## Machine interface and evidence

Commands planned for K09 are `resolve`, `build`, `test`, `inspect`, `explain`, `doctor`, and `evidence`; `dev` follows in K15. They are not currently implemented. Requested checks use `module:target:build` or `module:target:test`. JSON mode emits one `event` object per line, without terminal control codes or tool stdout. Event sequence numbers start at one and increase within a run; run IDs are unique across simultaneous invocations. Persist events before exposing them to clients. Inspection includes file ownership and configuration origins using JSON pointers.

Diagnostics contain category, stable code, scope and optional source location. Exit codes are 0 success, 1 failed check/infrastructure, 2 invalid configuration, 3 incomplete verification, 130 cancellation. Unsupported target/toolchain is an explicit gap. Tests retain stable identities and discovered/executed/failed/skipped counts. Unknown discovery counts remain null, never zero. A filter matching no tests is incomplete; an all-skipped scope does not prove execution. Test IDs are unique within module/target/runner scope; adapters must not fabricate identities from aggregate totals.

Verification binds requested and completed checks to the full source inventory, configuration, lock, runtime composition and toolchain identities. Cached compilation is distinct from tests executed now. A passing result requires every requested scope to complete, no failed actions/tests, and at least one executed test in each requested test scope. A result that detects changed inputs during execution is stale/indeterminate and cannot be current passing evidence. Prefer immutable snapshots; otherwise compare complete before/after manifests. Freshness queries re-inventory added/deleted/renamed and relevant untracked files, not only paths present in an old manifest. A Git revision is provenance, not sufficient input identity.

`dev` machine control will use newline-delimited JSON operations (`reload`, `test`, `quit`, `status`) on stdin and events on stdout. End-of-input closes the session. Source-plugin changes require owned work to stop and the launcher to compose a new native executable; no plugin hot loading. Failed builds preserve accurate identification of the prior running application snapshot. These are lifecycle contracts for K15, not implemented capabilities.

## Verification and ownership

Run `tools/test_contracts.py` with the pinned JDK/Kotlin/Native paths. `tools/check_schemas.py` uses the pinned development-only packages in `tools/schema-requirements.txt`. Generators reproduce checked-in schemas/examples; independent Python canonicalization produces vectors checked by the Kotlin/Native tests.

The integration agent owns `core/`, `schemas/`, launcher/CLI composition and contract changes. Subsequent implementation ownership is `execution/` for K03, `cache/` for K04/K07, and `resolution/` for K05. Implementations propose contract changes before editing shared types. Use separate worktrees and serial integration; each handoff includes reproduction, observed tests and unsupported cases. K14/K15 lifecycle gaps are not waived by passing the contract suite.
