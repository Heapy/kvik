# Dependency lock integration

This Kotlin/Native-compatible layer connects the v1 project model, K05 Maven/Gradle metadata resolver and K04 content store. It performs no lock-file IO and contains no JVM APIs.

```kotlin
val project = parseProjectConfiguration(parseJson(projectBytes.decodeToString()))
val policy = ResolverPolicy(pins = listOf(Coordinate.parse("org.jetbrains.kotlin:kotlin-stdlib:2.4.20")))
val effective = effectiveConfiguration(project, policy)
val locks = DependencyLocks(NativeContentStore(casDirectory), NativePomParser())

// Only an explicit resolve/update command gets a network transport.
val resolved = locks.resolve(effective, NativeHttpsTransport())
val publicationBytes = resolved.bytes() // Caller atomically publishes after explicit resolve/update.

// Build/test/locked/offline use has no transport parameter and never updates a lock or CAS.
val verified = locks.loadLocked(existingLockBytes, effective)
```

`effectiveConfiguration(...).digest` is the shared configuration identity for inspect, lock freshness and downstream actions. Its canonical document contains the complete validated project document, resolver policy version, exact global/scoped pins, resolver resource bounds, selected dependency scopes and expanded resolution domains. There are no implicit pins. A Kotlin stdlib alignment pin must be passed explicitly, as in the example. Changing a repository, compiler option, source-set declaration, pin, resolver bound or selected scope changes the identity. Equivalent scope/pin ordering is normalized; project declaration order is retained.

Default scopes cover each declared main/test compilation: JVM `java-api` and `java-runtime`, Native, JS and Wasm `kotlin-api` and `kotlin-runtime`. Callers can pass explicit `DependencyScope(module, target, scope, usage)` values to lock a subset. Prerequisite module API compilations and a test's own main compilation are included as separate domains. Tests own main dependencies even when their source set does not explicitly inherit main. Direct compile dependencies are visible to their owner; transitive module compile visibility follows only `exported=true` edges. Runtime traverses private and runtime-only edges too. Native `kotlin-runtime` is a **consumer link domain**, not a fabricated producer attribute: K05 still selects the published `kotlin-api` variant.

JS (`js`) selects only Kotlin IR variants with `org.jetbrains.kotlin.platform.type=js` and `org.jetbrains.kotlin.js.compiler=ir`. Wasm on JavaScript (`wasmJs`) requires `org.jetbrains.kotlin.platform.type=wasm` and `org.jetbrains.kotlin.wasm.target=js`. Both preserve the requested `kotlin-api` or `kotlin-runtime` producer usage and accept only `.klib` artifacts. Missing target/compiler attributes, Wasm WASI, legacy JS, JVM/Common/Native artifacts and POM-only fallback cannot satisfy these requests. Declare `kotlin-stdlib` and, for tests, `kotlin-test` explicitly; the resolver follows their published target redirects. No implicit standard-library version or dependency pin is added.

`ResolutionDomain(module, target, compilation, usage, purpose)` has this stable JSON shape:

```json
{"module":"sample","target":"jvm","compilation":"test","usage":"java-api","purpose":"dependencies"}
```

The default purpose is `dependencies`; `compiler-plugin` domains have `java-runtime` usage and request JVM host 25 variants, even for Native, JS and Wasm owners. Every `ResolutionRequest` binds a coordinate and real producer variant to its domain. `ScopedSelection(domain, selection)` retains K05's raw `LockedSelection`; persisted lock entries flatten these fields to `{domain,requested,variant,artifacts,metadata}`. Convenience getters expose `requested`, `variant`, `artifacts` and `metadata` without discarding domain identity.

`ScopedPin(domain, coordinate)` is public. `ResolverPolicy(pins, maxComponents, maxRequests, scopedPins)` keeps its prior positional arguments and appends the new list. The effective policy encodes `scopedPins` as a sorted array of `{domain,coordinate}`. A scoped pin overrides a global pin for the same component **only in that domain**. Duplicate component pins within a domain and pins naming unselected domains fail before resolution. No maximum-version or cross-domain alignment is inferred. For example, scoped annotations 23 pins for both test usages leave production's transitive annotations 13 untouched. Version conflicts within each domain still require an explicit compatible pin.

Resolver policy `kvik-maven-v3` records JVM compatibility explicitly. Consumer requests carry `org.gradle.jvm.version` derived from the compilation's options: default 11 or declared 11/17/21/25. The compiler graph and lock lookups use the same helper. Tests may specify different options, but their JVM target must support their own main output and every selected dependency-module output. A consuming module propagates its compilation target through its visible or runtime external closure; prerequisite modules retain their own independent API domains and targets.

Gradle metadata producer versions must be positive integers and no newer than the consumer. An absent producer version is unspecified. Multiple compatible candidates remain an ambiguity error; this bounded resolver does not implement Gradle's highest-compatible disambiguation. Plain Java library variants without a Kotlin platform attribute require Java usage, jar library elements and the supported JVM environment/bundling shape; they cannot satisfy a Native request. Unknown consumer attributes and unsupported producer semantics fail closed. POM-only jars accept the known consumer-version policy but cannot prove bytecode compatibility because POM metadata does not declare it. Legacy raw resolver requests with empty attributes still support unversioned producer metadata; versioned producers require an explicit target request. This policy intentionally changes effective identity and requires explicit resolve/update.

`resolve` collects compatible roots together per resolution domain, downloads through the injected bounded transport and durably stores each response in CAS. It returns a schema-compatible `DependencyLock` only after the same validation used by locked consumers. Failed resolution may leave reusable content-addressed blobs but cannot publish or overwrite a user's lock file.

`loadLocked` strictly parses lock v2 fields and mandatory domains, rejects duplicated selection/metadata/artifact entries and inconsistent identities across selections, checks the effective identity and exact ordered requests, and reads every referenced metadata/artifact digest from CAS. It then replays K05 against the lock's URL-to-digest mapping only and requires identical selections. This is validation of the recorded immutable graph: it never accesses current repository metadata or adds a newly selected component. It detects missing transitive closure entries, wrong variants/repositories, violated pins, reordered artifacts and extra metadata. A missing URL behaves as an offline 404 during the proof; missing bytes for a listed digest fail before replay. Missing/corrupt/stale locks require explicit resolution or repair and never trigger a download or lock rewrite.

The lock's digest is the SHA-256 and size of its canonical serialized bytes. `bytes()` emits `schemas/v1/contracts.json` definition `dependencyLock`, now version 2. Other contracts, including project configuration, remain version 1. Legacy unscoped lock version 1 is rejected with an explicit resolve/update instruction; it cannot prove which compilation selected a dependency and is never automatically relabelled. Lock parsing is bounded to 16 MiB, 8192 distinct URLs, 1 MiB per metadata blob, 64 MiB per artifact and 256 MiB of distinct referenced content. The caller owns bounded reading and atomic file publication; it must not write during ordinary build/test execution.

The supported metadata subset is exactly K05's. External plugin roots are included but their closures may still fail on unsupported metadata. Independent modules/compilations/usages may select different versions. Conflicts are resolved only within their recorded consumer domain. Native test/Kotest/KSP compatibility is not established by this integration. There is no dynamic dependency selection, repository refresh during locked use, implicit plugin resolution or unverified fallback.

Migration: omitted dependency `scope` means `compile`, omitted `exported` means `false`. This intentionally removes earlier hidden transitive module API promotion. Declare `exported=true` for public dependencies (or declare a direct consumer dependency), then explicitly resolve a v2 lock. `scope=runtime` cannot be exported. Existing target compiler options remain inherited by tests unless optional `testCompilerOptions` supplies a complete override; an empty override is meaningful. Native graph support still refuses differing visible/link closures rather than expose hidden link dependencies on its sole compiler library list.

Published Gradle metadata dependencies may declare `excludes` using exact group/module names or `*`. These exclusions apply to the descendants reached through that dependency, including redirects and constraints. A separate dependency path can still include the same library. Locks retain the metadata that declares the rules; dependency queries distinguish these edges as `metadata-exclusion` from explicit consumer policy overrides. Traversal depth and exclusion contexts are bounded. When metadata publishes both ordinary external and shadowed variants, the resolver selects compatible external variants and rejects a shadowed-only publication.

Maven dependency management supports bounded recursive BOM imports. Explicit management in the consuming POM overrides imported entries; earlier imports win over later imports, and imported management overrides inherited parent defaults. Imported POM identities are retained in the lock and used during offline replay. BOM properties are evaluated in their own model. Import/parent cycles and bounds are checked before traversal expands further. Profiles may add literal test-scope dependencies only when they cannot replace a production dependency, including dependencies whose scope comes from management. Other resolution-affecting profile content remains unsupported.
